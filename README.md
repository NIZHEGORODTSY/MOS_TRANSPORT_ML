# ML-ядро: прогноз задержки ТС за 10–15 минут

Для прогнозной точки `(tr_id, T)` модель предсказывает задержку (с) на первой остановке,
плановое прибытие на которую попадает в окно `(T+10 мин, T+15 мин]`.

## Результаты

Отложенный `labels_test.csv` (353 точки) и CV на train (5 фолдов по блокам «ТС × час»):

| Модель                                 | CV MAE, с     | test MAE, с   |
| -------------------------------------------- | -------------- | -------------- |
| прогноз 0                             | 88.3           | 103.3          |
| baseline`cur_dev_s`                        | 84.8           | 93.4           |
| `0.55 · cur_dev_s`                        | 75.5           | 86.0           |
| PyTorch GRU+MLP                              | 66.9           | 71.8           |
| CatBoost                                     | 65.7           | 69.7           |
| **ансамбль 0.4·NN + 0.6·CB** | **64.3** | **68.8** |

Производительность (CPU, 6 потоков): построение контекста по телеметрии за сутки ≈4 с,
инференс ≈2 мс на прогнозную точку (признаки + 5 сетей + CatBoost). Модель — 2.7 МБ.

## Как запустить

```bash
python -m venv .venv && .venv/Scripts/pip install -r requirements.txt
python -m ml.train --eval            # CV + проверка на test (~30 мин на CPU)
python -m ml.train --final --w-net 0.4   # обучение на train+test → artifacts/model, artifacts/submission.csv
python -m ml.predict                 # инференс сохранённой модели по validate/points.csv
```

Данные ищутся в родительской папке (`../train`, `../test`, `../validate`, `../labels`);
путь можно переопределить переменной окружения `MOSTRANS_DATA`.

## Как это устроено

1. **Map matching** (`ml/arrivals.py`). Каждая GPS-точка проецируется на перегоны «нитки
   графика» своего ТС (упорядоченные по плану остановки). Выбор перегона учитывает
   расстояние, курс и согласованность с предыдущей оценкой; отстой на конечной
   обрабатывается отдельно. Получаем задержку относительно плановой позиции в каждый
   момент. Сверка с фактами train: медианная ошибка ≈1 с, p90 ≈18 с.
   Дополнительно — радиусная детекция прибытий на остановки.
2. **Признаки на момент T** (`ml/features.py`, ~50 шт.): текущая задержка по GPS и её
   тренд за 5/10/15/30 мин, `cur_dev_s`, скорость/доля простоя/пройденный путь в окнах,
   время простоя, свежесть и покрытие телеметрии, число остановок/путь/плановое время
   до цели, паузы в графике впереди (отстой), каузальный профиль перегонов (насколько
   другие ТС до момента T отклонялись от плана на перегонах впереди), ETA по скорости.
   Для нейросети — последовательность из 40 шагов по 30 с (20 минут) состояния ТС.
3. **Модели** (`ml/models.py`): `DelayNet` — GRU по последовательности + MLP по
   табличным признакам, L1-loss, ансамбль 5 сидов; CatBoost (MAE). Смесь 0.4/0.6.
4. **Обучающая выборка** (`ml/dataset.py`): кроме официальных меток, моменты T на
   минутной сетке с той же постановкой (≈5× данных).

## Защита от утечек

* Признаки считаются только по телеметрии с `event_time ≤ T`, плановому расписанию
  (`validate/schedule_plan.csv`, без фактов) и подсказке `cur_dev_s`.
  Факты прибытий используются только как метки.
* **Синтетические ТС (`tr_id ≥ 9 000 000`) исключены**: это зашумлённые копии реальных
  ТС (корреляция задержек 0.99), их разметка раскрывает задержки test/validate.
* Расширенная выборка берёт только остановки из окон train-слотов; окна test/validate
  (и соседние неразмеченные слоты) исключены. При оценке на test модель не видит ни
  одной его цели.
* `tr_id` и время суток в признаки не входят (данные — один день, это был бы lookup).
* Флаг `manual_fill` целевой остановки (есть во входах validate, но описывает способ
  записи факта: 86% таких фактов = плану) по умолчанию **не используется**;
  включается `--use-manual-fill`.

> Замечание для организаторов: `validate/schedule_plan.csv` совпадает с
> `test/schedule.csv` без столбца факта, а `test/schedule.csv` и `train/schedule.csv`
> содержат `time_fact_begin` для всех 151 целевой остановки validate.
> Эта информация в решении не используется.
